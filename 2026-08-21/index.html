Done this week
01

72 sent Friday, then a deliberate hold on sending

Sending ran on Friday August 14 and put out 72. From there sending was held on purpose through the rest of the week, around Tuesday's alignment call with the team. The reason is lead quality upstream: unqualified and spam records are still landing in the lead base, and the call set up the fix, with Tom disqualifying them at the source and a reviewed flag so outreach only picks up leads that passed review. Holding the queue while that lands means the pool is not burned on records that would never convert, since every first touch spends a lead. Nothing was lost in the hold: everything queued rolls into the next build, and follow ups resume on schedule when sending does. The second sending domain that cleared warmup is being held back with the same logic, so the step from 90 to 180 a day lands together with the cleaner pool instead of scaling into the current one.

02

Root cause of the duplicate send closed out

The fault reported last week traced to how records were addressed rather than to the sending itself. Components were locating a lead by its position in the table, captured hours earlier when the day was planned, then writing back to that position at send time. If the table was reordered in between, the write landed on a neighbour. Every component that writes now resolves the lead by address at the moment of writing and skips rather than guesses if the record is missing or ambiguous. Records that had been marked against the wrong lead were identified by address, restored to their correct status and put back on the right follow up date.

03

Full opt out audit across the whole program history

The reply monitor was the last component still writing by position, and it is the one that closes an opt out, so a misplaced write there could leave a request unactioned. It was corrected and then verified against every record in the base with no mismatches. On top of the fix, every sending mailbox was swept back to the start of the program and each opt out request found is closed on the record. None are live. One of them had been sent from a different address at the same company, which only surfaces by resolving the conversation rather than the sender, so the sweep was built to work that way.

04

Daily integrity check running against the record set

A read only check now runs every morning and looks for follow up marks with nothing behind them, sends the record does not reflect, duplicate addresses, cadence overruns and missing rows. It reports only when it finds something. It exists because the issue above sat unnoticed for a week and surfaced by chance, and the standing assumption now is that a data fault will not announce itself.

05

Message level data hygiene tightened

A message by message review of a full day's build found a handful that should not have gone out, nearly all of them tracing to unusable values in the source record: greetings built from a fragment or a placeholder where a first name should be, and in a small number of cases a reference to a colleague that belonged to a different lead, because records with placeholder company values were being matched to each other. The writer now falls back to a neutral greeting when there is no usable name, the check enforces that in both directions, and colleague references no longer match on placeholder values. The automated review that reads every message before approval did not catch all of these on its own, which is why the fix went into the source of the data rather than into the review.

06

Row ceiling removed ahead of base growth

Parts of the system read the record set up to a fixed row limit while others read further. Past that limit the program would have kept sending while quietly no longer listening for replies on newer records. Every read is now open ended. The base sits at 1,324 and grew by 52 this week, so this was worth closing before it mattered.
